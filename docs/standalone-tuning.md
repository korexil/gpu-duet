# 独立服务端调试记录

接 xiaozhi 固件的板子实测时一条条改出来的东西，按「现象 → 原因 → 改法」记，有实测数据的写在改法里。都是默认值里已经带上的，这里留的是为什么。只记后端和声音链路上通用的事，具体某块板子的硬件问题不在这里。

## 识别

| 现象 | 原因 | 改法 |
|---|---|---|
| 喊唤醒词后回答变成韩文 | SenseVoice `language: auto` 对 1 秒多的短句猜错语种，转写成韩文字，LLM 跟着用韩文答 | ASR 固定语种（`asr.language: zh`），示例配置不再用 auto |
| 会话中再喊唤醒词，被当成一句话去问 LLM | 固件只在待机时上报唤醒词，会话中它只是普通音频 | 识别结果等于唤醒词时只应一声，不进 LLM |
| 识别偶发乱词、小声说话更明显 | 板子麦克风有宽带底噪（峰值 5000 左右，VAD 判 0，频谱无主频），信噪比差 | 送识别前整句过 GTCRN 降噪（sherpa-onnx 自带，0.5 MB，1 s 音频约 0.1 s） |
| 句首掉字 | 说完后 500 ms 的回声保护窗口把帧直接丢了，接得快第一个词就没了；VAD 判定开口也要几块 | 保护窗口内的帧进前摇缓冲，前摇 300 → 600 ms |
| 怀疑「没在收音」 | 看不到上行到底有没有东西 | `-v` 下每 5 秒记一行：帧数、有声帧、峰值、VAD 最高概率、底噪主频 |

## 说话

| 现象 | 原因 | 改法 |
|---|---|---|
| 一句话里忽大忽小 | tts-service 的整形只按每句开头 0.6 s 定一个增益，后半句模型自己变小 | 发帧前过慢速 AGC：压得快（60 dB/s）升得慢（6 dB/s），0.25 s 窗口响度 p90-p10 从 5.8～7.5 dB 降到 4.7～6.0 dB（三段固定回答，`python tools/agc_check.py`） |
| 段与段之间语调割裂、停顿明显 | 每段是独立的一次合成，模型看不到前后文；tts-service 每段结尾补 0.9 s 静音 | 段尾静音在发帧前修剪到 400 ms；首句不再在逗号处切出 |
| 整段 100 字一次合成，中途变成一字一句地念、响度漂 | 1.7B 模型跑长段落会换挡 | 一段 30～70 字（一两句）；第一段过 12 字遇句号就切，首声早 |
| 字幕先到、声音后到 | 文字一到就发了 `sentence_start`，合成第一块要 0.5～1.5 s | 字幕等这段第一块音频到了再发 |
| CustomVoice 加「节奏快慢有变化」指令，段间跳跃 | 每段独立理解一次「快慢有变化」 | 对话用克隆声音（参考音固定语速语调）；带指令的 CustomVoice 留给朗读/有声书 |
| 回答两三句就停，要追问「然后呢」 | 原来的提示词写死「两三句说完」，`max_tokens` 400 | 提示词区分闲聊和讲故事；`max_tokens` 1500 |
| 首声比预期慢 0.4～0.8 s | provider 自带的 GPU 轮流每 48 token 停下等 TTS 接句，独立服务端里 LLM 和 TTS 本来就串行 | `llm.turn_taking: false` |

## 试过不行的

- **上一段续写，第一轮**：把上一段合成音频重新编码当下一段的 ICL 提示，从第二段起语速掉到 1.5～3 字/秒、撞生成预算、念成数字。后来查明不是路线问题：写提示 JSON 时 `json.dumps` 默认把中文转义成 `\uXXXX`，引擎的 JSON 读取器不解转义，模型把转义串逐字念了出来；`ensure_ascii=False` 后正常。教训是实验失败先核对引擎到底收到了什么，再下路线结论。另一个真坑：重编码要装音频编码器，8 GB 显卡上和 LLM、TTS 一起会溢出到共享内存，实验只能在 CPU 上做；直接取引擎生成的 codes 当提示则不需要编码器，见 [upstream.md](upstream.md#实验中codes-continuation-分支未合入) 的 `codes-continuation` 分支。
- **分段带 300 ms 前瞻做响度**：和不带前瞻比没有改善，不用。

## 要不要唤醒词

默认 `idle_close_s: 0`：连接一直开着、一直在听，开口就答。xiaozhi-esp32-server 的默认是没人说话两分钟就断开、板子回待机、下次要喊唤醒词——一直摆在桌上的设备没必要，而且重连后第一句总要等。想要那种模式就把它设成秒数。
