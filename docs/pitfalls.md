# 踩坑记录

环境：RTX 4060 Laptop 8 GB、16 GB 内存、Windows 11；终端 M5Stack Atom EchoS3R（ESP32-S3）；服务端 xiaozhi-esp32-server（Docker）。对话语言是日语，结论大多与语言无关。

---

## 一、「模型变笨」：先查输入，再换模型

**1. 系统提示词本身在制造症状。** 提示词里写了「简短回答」「不确定就反问」「紧急情况请联系他人」，结果回答短、反问把话聊死、问它自己的事也跳到求助建议。换了几个模型都一样。先读一遍系统提示词。

**2. ASR 的 JSON 原样进了对话历史。** FunASR 返回 `{"content","language","emotion"}`，未启用声纹时整串 JSON 被当成用户消息。修复：[#3411](https://github.com/xinnan-tech/xiaozhi-esp32-server/pull/3411)。

**3. SenseVoice 识别日语时按词带空格**（`今日 の こと を`）。修复：[#3412](https://github.com/xinnan-tech/xiaozhi-esp32-server/pull/3412)。

**4. 4B 模型放 CPU + 温度 1.0 + 2048 上下文，就是弱。** 换 Gemma 4 E4B（QAT q4_0）全层上 GPU：解码 61～66 tok/s，首字 0.1～0.2 s（随提示长短：36 token 约 0.1 s，400 token 约 0.2 s；复现方法见 [benchmarks.md](benchmarks.md#复现)），同一套提示词下质量明显更好。

## 二、小模型的提示词

**5. 提示词里的例子会被反复照抄。** 列了几个可聊的日常话题（窗外、窗帘、电车……），20 次讲自己的一天，20 次提到「窗」。去掉例子后 0 次。

**6. 句子越长，TTS 余量越小。** 在下面「评测方法」的对话集上，不加约束时句长中位数 19 字、最长 53 字。提示词写明「一句只说一件事，约 15 字，及时用句号断开」后降到 12 / 27 字（benchmark 的问题要求讲长一点，同样两种提示词下是 40 / 13.5 字，见 [benchmarks.md](benchmarks.md#benchmark只有-gpu-轮流能把断音压到-0)）。每次 TTS 调用变短，断音减少，但不能消除：benchmark 里只缩短句子，6 次仍有 4 次断音（第 9 条）。

**7. 小模型约 75% 的回答以提问结尾。** 只靠提示词压不住，还会和其他要求互相拉扯。如果不想要，在上一轮以问句结尾时，往**最后一条用户消息末尾**附一条备注（provider 的 `question_rest_note`）。放末尾而不是系统提示里，前缀 KV 缓存不受影响。实测降到 9～26%，备注被念出来 0/66。

**8. 「不要用符号」会被理解成连标点也不用。** 整句没有句号，TTS 分句和停顿全乱。要写「标点照常用」。

**提示词里不要写：**
- 「简短回答」「不确定就反问」：模型会照做，回答变短，反问把话聊死。
- 话题例子、示范回答：会被反复照抄。
- 「不要用符号」：连标点一起丢。
- 「每次以提问结尾」/「不要总是提问」：前者每句都问，后者压不住，用 `question_rest_note`。

**评测方法：** 不看单句。用约 5 组、每组 4～5 轮的真实对话（寒暄、讲长一点、接着讲、情绪低落、名字记忆），每组跑几个随机种子，统计：以提问结尾的比例、句长（中位数/最大值）、同一话题重复次数，以及你在提示词里禁止的内容出现了几次。

## 三、一块 8 GB GPU 上同时跑 LLM 和 TTS

**9. 同时跑，TTS 跟不上实时。** TTS 单独 RTF 约 0.6；LLM 同时解码时，第一句 RTF 升到 1.1～1.6，开头就断。
- 给 LLM 限速（20 或 14 tok/s）：无效，RTF 仍约 1.4。TTS 逐帧解码，大量很小的同步 kernel，LLM 只占一点时间片，TTS 每一步都要等。
- 调 WDDM GPU 调度优先级（`D3DKMTSetProcessSchedulingPriorityClass`）：对 CUDA 计算无效。
- **轮流用 GPU**：LLM 生成到句末就停，等 TTS `/health` 不再 `busy` 再继续。两者合计只需约 75% 的 GPU，串行够用。[benchmark](../bench/README.md)（每格 6 次，中位数）：

  | | 首声 | 断音合计 | 有断音 |
  |---|---|---|---|
  | 无调度 | 3.20 s | 2.27 s | 6/6 |
  | 仅缩短句子（+0.9 s 停顿） | 2.62 s | 0.48 s | 4/6 |
  | 仅 GPU 轮流 | 1.83 s | 0 | 0/6 |
  | 缩短句子 + GPU 轮流 | 1.42 s | 0 | 0/6 |

  早先单次测量时以为「句子改短、加停顿后不轮流也不断音」，重复 6 次后不成立。断不断音取决于回答多长：只缩短句子时，音频 34 s 以内的 2 次都没断，35 s 以上的 4 次全断（0.45～1.55 s）。LLM 一直在后台生成，回答越长，TTS 被拖慢的时间越长，前面攒下的余量迟早用完。早先那次只测了一次，也没留下回答长度，很可能碰上的是短回答。实现：`server/core/providers/llm/llamacpp_paced/`；测量：`bench/run.py`。

**10. 不要用 chat 接口的 assistant 预填来分块续写。** 模板会去掉预填末尾的空白，续写和一次性生成不一致。改用 `/completion`，prompt 为 `[渲染好的模板字符串, *已生成的 token id]`：前缀逐 token 一致，KV 缓存命中。`stop_type == "eos"` 时，最后的结束 token 会被 `/detokenize` 还原成 `<turn|>` 之类的文字，要去掉。

**11. GPU 空闲降频拖慢第一句。** 空闲 8 s 后 GPU 在 P8（210 MHz），TTS 首块 0.64 s；热态 P0 只要 0.17 s。

**12. 显存超额时，Windows 驱动不报错，只会悄悄变慢。** 两个 TTS 实例同时在 GPU 上时，llama-server 大部分显存被挪到共享系统内存，解码 66 → 45 tok/s，进程不崩。排查：任务管理器看每个进程的「专用 GPU 内存」。重启受影响的进程即可装回显存。

**13. 内存也要算账（16 GB）。** PyTorch 版 TTS 进程 8.9 GB 私有内存，大部分被换到页面文件，每次合成都从磁盘读回，又慢又卡。换 C++ 原生引擎（`native-tts/`）后显存约 4.0 GB，内存也小得多。另外 Ollama 启动 llama-server 用的是 `--load-mode none`，权重读进私有内存而不是 mmap（见过 4.7 GB）；Docker Desktop 的 WSL 虚拟机约 3.4 GB。三样同时开时，可用内存曾被压到 141 MB，每秒换页 6 万次。

## 四、逐句合成后的声音

**14. 句与句之间忽大忽小**（一段回答内差 5～7 dB）。每句用开头 0.6 s 定一个增益，整句不变。两种不行的做法：
- 句内每 0.32 s 调一次增益：和句子本身的轻重音打架，听起来在抽动。
- 沿用上一句的增益：上一句偏轻、这句开头偏响时，第一个字被放大成爆音。

**15. 停顿忽长忽短**（0.2～1.25 s）。模型每句自带 0.4～0.7 s 开头静音，句尾也长短不一。切掉开头静音，句尾统一补齐。xiaozhi 服务端交给 TTS 前会去掉每段末尾的标点，只能按句子长短区分停顿。

**16. 爆音、破音。** tanh 软削顶在小喇叭上失真；Opus 编解码还会把 -0.4 dB 的峰值推到满幅。改用平滑限幅器，峰值留在 -6 dBFS；响度不够就调设备喇叭音量，不要推数字信号。

**17. 每次开口前「啪」一声。** 设备空闲时关功放，开口时上电。模型自带的开头静音原本盖住了这一下，切掉后就露出来。修法：静默超过 1.5 s 后的第一句，前面留 0.3 s 静音。

**18. 设备音量可由服务端设置**：MCP 工具 `self.audio_speaker.set_volume`，固件默认 70。

**19. 分句会切开引号**（`「わぁ！」って` 被切成两段）。修复：[#3413](https://github.com/xinnan-tech/xiaozhi-esp32-server/pull/3413)。

## 五、唤醒词（非中英文的名字）

**20. 用 ESP-SR MultiNet 的拼音近似一个日语名字，命中率很低。** 测法：VOICEVOX 10 个声线合成 60 条，电脑外放给板子听，读串口计数（`tools/wake_test/`）。

| 方案 | 命中 | 误唤醒（20 条易混词） |
|---|---|---|
| MultiNet5（中文，量化版）5 条拼音，阈值 0.2 | 3/60 | 0/20 |
| 同上，24 条拼音变体，阈值 0.06 | 29/60 | 1/20 |
| 同上，35 条，阈值 0.06 | 28/60 | 2/20 |
| MultiNet5，阈值 0.01 | 9/60 | 0/20 |
| MultiNet7（中文），36 条，阈值 0.08 / 0.04 | 20/60 / 18/60 | 0/20 |
| **服务端 SenseVoice 识别同一批音频** | **53/60** | **0/20** |

阈值和命中率不单调，同一批音频多跑几次也会浮动。命中最多的拼音是中文模型「听到」的样子（如日语「の」被听成 nao），不是按读音拼出来的。

**21. 所以把唤醒放到服务端**（`server/core/handle/wakeGate.py`）：板子保持一个常开的收音会话，每段话都在服务端做 ASR，听到名字才回应。
- ASR 常把名字识别成**同音汉字**，`wake_patterns` 要把同音写法和常见误识别都加进去。
- 上游有「无声音超时」的二道关闭，会断掉常开会话；补丁里闸门开启时会刷新活动时间。
- 房间里别的说话声也会被识别，只是不回应。CPU 开销每段约 130 ms。

**22. 想换更大的 MultiNet，assets 分区放不下**（2.25 MB）。不用 OTA 的话可以去掉 `ota_1`，把 assets 扩到约 5 MB，`ota_0` 不动。先用 esptool 读 otadata，确认当前从 `ota_0` 启动。唤醒配置在 assets 分区的 `index.json` 里，只重刷这个分区即可，不用重编固件（`tools/esp32/xiaozhi_assets.py`）。

**23. 读串口前把 DTR、RTS 设为 False**，否则会复位板子。

## 六、编译

**24. nvcc 在 Windows 上会撞 260 字符路径限制**，报错 `Could not open output file ...cu.obj.d`。编译目录用短路径。

## 七、测量

**25. 同一个 seed 在 llama-server 上不一定生成同样的文字。** slot 里缓存的前缀长度不同，批的形状就不同，logits 有细微差异，采样从某个 token 起分叉。实测同 seed 连续三次：第一次和后两次不同。每次先发一个无关的 `cache_prompt: false` 短请求把缓存顶掉，三次完全一致。做 A/B 对照时要这样做（`bench/run.py`）。

**26. 测量时先确认 GPU 上只有你要测的进程。** 一个守护任务在测试中途把旧的 TTS 重新拉起，两个 TTS 同时占着显卡，合成卡死；之后 llama-server 的权重被挪到共享内存（第 12 条），停掉多余进程后也不会自己回来，要重启 llama-server。任务管理器里看每个进程的「专用 GPU 内存」。

## 八、安装脚本（Windows）

**27. Windows PowerShell 5.1 里，脚本输出一重定向就报错退出。** `$ErrorActionPreference = 'Stop'` 时，git、cmake、pip、`vcvars64.bat` 往 stderr 打的普通进度信息（如 `Cloning into...`）会被当成致命错误。直接在终端里跑没事，`*> build.log` 存日志就会在克隆这一步失败。改法：调用外部程序时临时改成 `Continue`，只看退出码（`native-tts/build.ps1` 的 `Invoke-Native`）。顺带：克隆失败一半时目录已经存在，下次运行会把半截的源码当成已完成，所以改成补丁打完才写一个完成标记。

**28. `git clone --filter=blob:none` 之后 `git checkout <commit> -- scripts` 会失败**，报 `unable to read sha1 file`，部分克隆没有按需拉取文件内容。只要固定提交里的几个文件时，用 `git init` + `git fetch --depth 1 <url> <完整 SHA>` + `git checkout FETCH_HEAD -- scripts`（`native-tts/setup-models.ps1`）。

**29. venv 放在太深的目录，装 torch 会失败**：`OSError: [WinError 206] 文件名或扩展名太长`。torch 依赖里有很长的测试文件路径，加上 venv 本身的路径就超过 260 字符。venv 放在短路径下（比如盘根下的 `venv` 目录），或者在系统里开启长路径支持。

## 九、C 接口（Python ↔ C++）

**30. 只比 `sizeof` 不算校验 ABI。** 结构体里两个同宽字段调换顺序、`int32` 换成 `float`，大小都不变，校验照样通过，然后在错误的偏移上读内存。桥接库改成导出两张表：每个结构体的大小加**每个字段的偏移**（抓重排、增删），和每个字段的**类型码**（抓同宽度换类型）；Python 用 ctypes 的 `.offset` 和字段类型算出同样两张表逐项比对（`native-tts/` 补丁的 `qwen3_tts_bridge_abi_layout` / `qwen3_tts_bridge_abi_types`、`tts-service/native_engine.py` 的 `check_abi`）。CI 在 Linux 和 Windows 上各编一遍 CPU 版再跑这个比对。

**31. C++ 异常穿过 C 边界会直接杀掉宿主进程。** `extern "C"` 的函数里抛出的异常没人接，Windows 上整个 Python 进程退出，连一行错误都没有。桥接库的每个导出函数都包一层 `try/catch`，异常变成 `success=0` 加错误文本，或者 `get_last_error` 里的一条消息。

**32. 模型路径含非 ASCII 字符时打不开文件。** 上游用 ANSI `fopen` 和窄字符 `std::filesystem::path` 打开模型、声音提示和参考音，路径却是 UTF-8 传进来的；日文 Windows 的用户目录就是这种路径，`fopen` 会去找一个按 CP932 解读的乱码文件名。补丁里的只读映射一开始只是拒绝加载，后来发现其余张量也会在同一个地方失败，所以统一改成先转宽字符再用 `_wfopen` / `CreateFileW`（`src/common/utf8_path.h`），用日文目录名实测通过。
